     3	## Repository Role
     4	
     5	This repository is a reusable baseline for AI-assisted product development. It is intended to be
     6	cloned, initialized for a specific project, and evolved toward documented goals with a human team
     7	member and AI coding agents.
     8	
     9	Do not treat chat history as build authority when methodology or project authority documents apply.
    10

    12	under `docs/methodology/dev-skills/`. The engineering, task lifecycle and
    13	independent validation policies under `docs/policies/` supplement GenDev.
    14	Read `docs/policies/dev-board-integration.md` for the task/gate boundary.
    15	The board is tooling; task state never substitutes for product gate approval.

    20	`docs/resources/evolution/v3-migration/README.md`. Do not initialize a product

    66	## Agent Start Contract
    67	
    68	At the start of a task, the lead agent must establish repository state before
    69	editing methodology or project artifacts:
    70	
    71	```bash
    72	./scripts/gendev-doctor.sh
    73	```
    74	
    75	The doctor's prerequisite report is contract, not decoration: GenDev requires
    76	bash 4+, git, python3, and ripgrep (rg). If the doctor reports a missing
    77	prerequisite (exit code 3), stop and have it installed before any methodology
    78	work; do not substitute another tool or emulate the missing one.
    79	
    80	If the project is initialized, also run:
    81	
    82	```bash
    83	./scripts/project-state.sh
    84	```
    85	
    86	Use the output to report the current gate, next artifact, required approver, and
    87	recommended validation. If `docs/project/` is missing, initialize the project
    88	before product implementation. If current state is unclear or authority is
    89	missing, stop and ask for human disposition rather than inferring approval.
    90	
    91	For canonical late-lifecycle artifacts, prefer the generator over ad hoc files:
    92	
    93	```bash
    94	./scripts/new-artifact.sh --kind deployment-readiness
    95	```
    96	
    97	The human may set the collaboration mode in plain language, such as:
    98	
    99	```text
   100	Lead proactively.
   101	Use approval-gated mode.
   102	Stay advisory.
   103	Proceed execution-focused.
   104	```
   105	
   106	The lead agent must follow the selected mode while preserving required human approvals. Proactive
   107	mode does not bypass gate approvals, security approvals, or production approval.
   108	
   109	For short prompts such as `Let's begin`, `What's next?`, `Continue`, `Proceed`, `Pause`, and
   110	`Resume`, follow `docs/methodology/guides/start-and-next-step-protocol.md`.
   111	
   112	When coordinating sub-agents, follow `docs/methodology/guides/subagent-coordination-protocol.md`.
   113	Sub-agent output is advisory until accepted into active project documents or approval records.
   114	
   115	When accepted authority must change, follow
   116	`docs/methodology/guides/amendment-and-regression-protocol.md`. Do not keep moving forward with
   117	stale authority, and do not regress gates unless the amendment invalidates gate entry conditions.
   118	
   119	When enforcement class, gate protection, or implementation-path controls matter, follow
   120	`docs/methodology/guides/enforcement-contract.md`. Attested enforcement is valid at baseline, but
   121	the active project must declare its class in `docs/project/project.yaml`.
   122	
   123	When project scale, gate combination, or GenDev Lite matters, follow
   124	`docs/methodology/guides/gates.md`. The active project must declare `scaling.blast_radius_class`
   125	as `C1`, `C2`, or `C3` in `docs/project/project.yaml`. Enforcement class and blast-radius class are
   126	different controls.
   127	
   128	Use `docs/project/project.yaml` as the active project control-plane summary and
   129	`docs/project/approvals/gate-log.md` as the durable approval history. Do not treat a gate as
   130	approved unless the required approver, approval date, evidence, and risk disposition are recorded.

   183	## Implementation Rules
   184	
   185	### Board and Code-Generation Start Contract
   186	
   187	Before generating or modifying product code:
   188	
   189	1. Run the GenDev doctor and project-state commands, then
   190	   `uv run --no-project --with-requirements requirements-devboard.txt python scripts/devboard.py validate` and `next`.
   191	   Inspect the selected task with `show <task-id>`.
   192	2. Confirm the board task is `started`, has `implementation_authority: granted`, and names
   193	   the current feature branch. `approved` permits execution preparation; it does not begin
   194	   product code generation. Check the actual human direction behind the recorded approval.
   195	3. Read the tracking index and its links to accepted canonical GenDev authority. Confirm the
   196	   current project gate and phase checkpoints permit that implementation scope.
   197	4. Read the approved phase build plan, tactical plan, construction directive, and verification
   198	   plan. Each work unit needs exact scope, non-goals, requirements, tests, and stop conditions.
   199	   Only the documented maintenance route applies to eligible non-product maintenance.
   200	5. Reconcile task state, branch/checkout, authority revisions, source, tests, and evidence
   201	   before proceeding if they disagree. No directory, label, role flag, or tool result supplies
   202	   missing authority.
   203	
   204	The board tracks tasks through queued, approved, started, completed, and accepted. Only the human
   205	approves or accepts task scope. Task state and recorded delivery never substitute for GenDev
   206	approval. Preserve unrelated changes and local runtime data; do not clean or broad-stage them.
   207	
   208	### Candidate Review and Acceptance
   209	
   210	After authorized product generation, freeze a stable candidate commit when committing is
   211	authorized, then obtain fresh-context, read-only conformance review. Supply pinned authority,
   212	the directive, exact candidate/diff, acceptance criteria, and required evidence; exclude the
   213	builder's transcript, private reasoning, and conclusions. The reviewer returns exactly
   214	`VERIFIED`, `CHANGES_REQUESTED`, or `BLOCKED` with reproducible evidence.
   215	
   216	Work remains `started` through required review and bounded remediation. A changed candidate or
   217	authority makes the prior result stale and requires fresh review. Propose `completed` only
   218	after the applicable independent `VERIFIED` result; only the human records `accepted`.
   219	If a candidate cannot yet be frozen, report that limit rather than claiming formal verification.
   220	Eligible documentation maintenance follows its separately recorded scope and checks.
   221	
   222	Review does not authorize reviewer edits, automatic unbounded remediation, additional delegates,
   223	push, merge, release, deployment, credential disclosure, or external effects. Keep board tracking
   224	indexes and their evidence in the lanes described by the local lifecycle policy; canonical
   225	GenDev authority stays under `docs/project/` through tracking moves and archival.
   226	
   227	
   228	Before meaningful code generation, confirm that the active project has enough documented authority
   229	to answer:
   230	
   231	- what is being built;
   232	- why it is being built;
   233	- who it is for;
   234	- what is in scope;
   235	- what is out of scope;
   236	- what architecture governs it;
   237	- what security and governance rules apply;
   238	- what tests or UAT checks prove it works;
   239	- what documentation must be reconciled afterward.
   240	
   241	Do not implement deferred features, silently widen scope, weaken security/governance behavior,
   242	or mark planned behavior as implemented unless it is actually implemented and verified.
   243	
   244	## Examples Are Not Active Authority
   245	
   246	`docs/resources/examples/` contains example methodology artifacts. It is not the active project for a new
   247	clone. Do not cite example PRDs, architecture docs, traceability matrices, implementation evidence,
   248	source paths, tests, or UAT claims as local project authority unless the active project explicitly
   249	adopts that material and matching local source/test files exist.

   251	## Verification and Close-Out
   252	
   253	When implementing product code, follow the active project verification commands. If commands are not
   254	yet defined, create or update the relevant phase plan before proceeding.
   255	
   256	Run the methodology checker before implementation, phase close-out, and handoff when applicable:
   257	
   258	```bash
   259	./scripts/check-methodology.sh
   260	```
   261	
   262	For each completed phase, update:
   263	
   264	- test or UAT evidence;
   265	- code review findings or review status;
   266	- remediation status, if applicable;
   267	- as-built close-out;
   268	- traceability matrix;
   269	- deferred item list and known limitations.
   270	
   271	Report skipped verification honestly with the reason.

================ docs/methodology/constitution/gendev.md ================
     1	# AI-Assisted Software Engineering Documentation Constitution
     2	
     3	Status: Reusable Standard  
     4	Version: 1.0.2
     5	License: CC BY 4.0 for documentation; see repository `LICENSE`.
     6	Audience: Product owners, architects, engineering leads, AI-assisted coding operators, reviewers, and implementation agents  
     7	Scope: Documentation, traceability, build governance, testability, and AI-assisted implementation process for software projects
     8	
     9	## Purpose
    10	
    11	This constitution defines a reusable documentation-first engineering method for building reliable, testable software with AI-assisted software engineering tools such as Codex, Claude Code, or similar implementation agents.
    12	
    13	The method exists to ensure that software is not built from vague intent, chat history, or isolated prompts. It requires a traceable chain from vision to requirements, architecture, implementation planning, code generation, testing, review, remediation, and as-built documentation close-out.
    14	
    15	The core objective:
    16	
    17	```text
    18	build software from explicit authority,
    19	verify it against testable requirements,
    20	preserve traceability from intent to implementation,
    21	and prevent AI-assisted phase drift.
    22	```
    23	
    24	## Core Principle
    25	
    26	No meaningful implementation should occur unless the implementer, human or AI, can answer:
    27	
    28	```text
    29	what are we building?
    30	why are we building it?
    31	who is it for?
    32	what is in scope?
    33	what is out of scope?
    34	what architecture governs it?
    35	what security and governance rules apply?
    36	what tests prove it works?
    37	what documentation must be reconciled when complete?
    38	```
    39	
    40	If those answers are not documented, the project is not ready for code generation.
    41	
    42	## Technique Neutrality
    43	
    44	This is a first-order principle of the methodology. The rules that follow —
    45	canonical naming, the documentation scaffold, the supporting-artifact mechanism,
    46	and the reference discipline — are its consequences.
    47	
    48	GenDev governs how work earns authority and how that authority is gated,
    49	reviewed, and kept coherent. It does not specify how the work is conceived,
    50	modeled, or built. The method is the authority-and-gate machinery; the technique
    51	is everything about how a team designs and constructs — object-oriented,
    52	data-driven, event-driven, or an approach not yet invented. The method must not
    53	couple itself to a technology stack or to a software-engineering approach.
    54	
    55	The blend point is the artifact. A technique's artifacts enter the methodology
    56	through a fixed authority-and-reference discipline: they are named, located,
    57	provenanced, and referenced by the method's rules, and because they obey that
    58	discipline the method can gate and coherence-check them without knowing which
    59	technique produced them. The method is opinionated about how an artifact earns
    60	authority; it is silent about what the artifact contains.
    61	
    62	Stated as a maxim: the method does not specify the technique, but the technique
    63	must blend with the method.
    64	
    65	Every other rule in this constitution that concerns artifact structure,
    66	naming, scaffolding, or references must remain consistent with this principle. A
    67	future rule that couples the method to a specific technology stack or engineering
    68	approach violates it.
    69	
    70	## First Principles of Code Quality
    71	
    72	This is a first-order principle of the methodology, and a deliberate complement
    73	to Technique Neutrality. Technique Neutrality states what the method is silent
    74	about: how the work is conceived, modeled, and built. This principle states what
    75	the method is not silent about: six properties the produced code must have,
    76	whatever technique produced it.
    77	
    78	These six are constitutional, not technical. They do not tell a builder how to
    79	design or which pattern to reach for. They state properties the result must hold
    80	regardless of how it was built, the same way "the architecture must cohere with
    81	the PRD" is a property of the result and not a technique for producing it. They
    82	sit on the method side of the Technique Neutrality line, alongside blast radius
    83	and accountability, not on the technique side alongside object-oriented or
    84	data-driven design.
    85	
    86	The six:
    87	
    88	```text
    89	YAGNI  You Aren't Gonna Need It. Build only what a current, approved requirement
    90	       asks for. Do not build for a requirement that does not yet exist.
    91	KISS   Keep It Simple. The simplest structure that satisfies the requirement is
    92	       the correct one, not the most general or most extensible.
    93	DRY    Don't Repeat Yourself. Logic that already exists is called, not rewritten.
    94	SRP    Single Responsibility. Each unit does one coherent job.
    95	LA     Least Astonishment. Behavior matches what an obvious reading of the
    96	       requirement would lead a reader to expect.
    97	NAA    No Undeclared Abstractions. Any authority-bearing abstraction the build
    98	       introduces must already be declared in approved upstream authority or be
    99	       introduced through an amendment before use. A build implements the
   100	       approved model. It does not silently expand behavior, authority boundaries,
   101	       or trust model.
   102	```
   103	
   104	These principles exist because a generator, left unconstrained, violates all six
   105	by default. Verbosity, over-generalization, duplication, conflated
   106	responsibilities, surprising behavior, and unrequested abstraction are the
   107	standing tendencies of machine generation, not occasional lapses. A test suite
   108	does not catch them, because all six can be present in code that passes every
   109	test. The method therefore states them explicitly and binds them at the points
   110	where generation happens.
   111	
   112	The binding mechanism follows from this. These six are restated in full in every
   113	construction directive's anti-drift section, at the point of generation, every
   114	phase, without exception. They are checked at code review by a conformance
   115	reviewer operating under the reviewer-independence rule.
   116	
   117	For this methodology, NAA applies to authority-bearing abstractions:
   118	
   119	```text
   120	domain or business concepts and rules
   121	persisted, shared, externally exchanged, or security-sensitive fields
   122	public, externally consumed, or cross-component interfaces
   123	architectural boundaries (components, services, storage, ownership)
   124	trust, identity, authorization, audit, data sensitivity, and lifecycle control
   125	```
   126	
   127	A build may add implementation-local detail without amendment only when the build
   128	task already authorizes it and all of these conditions hold:
   129	
   130	```text
   131	it is private to a component or test scope
   132	it does not add product behavior, policy, or observable semantics
   133	it does not add shared, persisted, or externally exchanged state
   134	it does not add or alter public or cross-component contracts
   135	it does not change acceptance, governance, or phase boundaries
   136	it is proportionate under YAGNI, KISS, DRY, and SRP
   137	```
   138	
   139	Typical allowed categories are private helpers, local adapters, internal value
   140	types, framework-generated types, test fixtures, fakes, and mocks.
   141	
   142	Every other rule in this constitution that concerns what a build produces must
   143	remain consistent with these six.
   144	
   145	## Applicability
   146	
   147	Use this standard for:
   148	
   149	```text
   150	new product development
   151	feature phases
   152	large refactors
   153	security-sensitive systems
   154	agent platforms
   155	governance or permission subsystems
   156	CLI-first UAT projects
   157	AI-assisted implementation workflows
   158	projects where traceability and testability matter
   159	```
   160	
   161	This standard may be scaled down for small work, but the traceability chain should not be abandoned.
   162	
   163	## Verification-First Principle
   164	
   165	A project must define how it will know the work is correct before it builds the work, and a human
   166	must approve that definition of correctness in a form precise enough to test. Verification is a
   167	design input, not a downstream check. This principle is the reason "what tests prove it works?" is
   168	one of the questions the Core Principle requires answered before code generation.
   169	
   170	Verification answers three distinct questions. They are exhaustive: there is nothing to verify
   171	outside the requirement, the design, and the code.
   172	
   173	```text
   174	behavioral:     does the implementation do what is required, including the negative and edge
   175	                cases, not only the happy path? (user acceptance is the user-facing slice)
   176	design:         does the design hold under the conditions it must survive (partition, network
   177	                loss, security boundary, degradation, scale, evolution)? this is evaluable the
   178	                moment the design is written, before any code exists
   179	implementation: is the code sound as an artifact and durable under change (correct types and
   180	                contracts, no brittle assumptions that erode over time)?
   181	```
   182	
   183	What unifies the three is that each asks whether the work is correct under conditions the happy
   184	path does not reveal: the requirement's edges, the design's failure modes, and time.
   185	
   186	Verification-First is a methodological commitment, not a technique. The method requires the
   187	verification and gates it; it does not prescribe how the verification is produced. Test-driven,
   188	behavior-driven, acceptance-test-driven, property-based, and classic test-after development are
   189	techniques, and the method stays neutral on them under the same reasoning as Technique Neutrality.
   190	The philosophy is methodology; the practice is technique. The maxim: define how you will know it
   191	works before you make it work.
   192	
   193	This standard scales with blast radius (a small project may answer the three questions briefly,
   194	including an honest "no failure modes beyond single-process operation"), but the questions should
   195	not be left unasked.
   196	
   197	## Blast-Radius Scaling Principle
   198	
   199	GenDev ceremony scales with the blast radius of the work. Blast radius means the plausible impact
   200	of a wrong requirement, bad implementation, unsafe deployment, missed review finding, or agent
   201	misstep.
   202	
   203	Every initialized project should declare a blast-radius class in `docs/project/project.yaml`:
   204	
   205	```text
   206	C1 Contained
   207	  Internal tools, reversible outputs, no sensitive data, low operational risk.
   208	
   209	C2 Standard
   210	  Default product work, moderate operational or data risk, ordinary production release discipline.
   211	
   212	C3 Critical
   213	  Regulated data, irreversible actions, external integrations, production-sensitive automation,
   214	  agentic runtime behavior, or high operational impact.
   215	```
   216	
   217	Scaling down is legitimate only when required content remains explicit. A C1 project may combine
   218	early gates or artifacts, but it must still define the problem, requirements, architecture
   219	assumptions, security assumptions, build plan, verification, approval, and close-out evidence.
   220	Scaling down does not waive production approval, rollback thinking, or security assumptions when
   221	the product is deployed or touches meaningful data.
   222	
   223	Scaling up is mandatory when exposure increases. A C3 project should not combine lifecycle gates.
   224	It should use stronger independent review, evidence sampling, explicit override discipline, and
   225	stricter enforcement than the baseline.
   226	
   227	Gate combination must be recorded with a justification, class, affected gates, preserved content,
   228	approver, and evidence path. If the justification is missing, the methodology treats the combined
   229	gate path as a process risk, not as an informal shortcut.
   230	
   231	## Version-Control Assumption
   232	
   233	This methodology assumes a version control system with immutable revision identifiers, diffable
   234	history, and branch isolation. Git is the default implementation, but any system with equivalent
   235	properties can support the methodology.
   236	
   237	Revision control is not incidental. Provenance, amendment, review independence, enforcement, and
   238	as-built close-out all depend on being able to identify what changed, when it changed, and what
   239	authority governed the change.
   240	
   241	## Constitutional Rules
   242	
   243	### Rule 1: Documentation Is Build Authority
   244	
   245	AI-assisted implementation must be grounded in authoritative documents.
   246	
   247	Implementation prompts must cite or summarize the relevant authority:
   248	
   249	```text
   250	vision or product goal
   251	PRD requirements
   252	architecture specification
   253	governance/security rules
   254	phase build plan
   255	tactical implementation plan
   256	acceptance criteria
   257	test expectations
   258	documentation close-out requirements
   259	```
   260	
   261	The AI builder must not infer new product scope from casual conversation unless the operator explicitly authorizes that change and updates the relevant documentation.
   262	
   263	### Rule 2: Traceability Is Mandatory
   264	
   265	Every material requirement must map forward to implementation and verification.
   266	
   267	Minimum traceability chain:
   268	
   269	```text
   270	requirement
   271	  -> architecture rule or design decision
   272	     -> build-plan scope item
   273	        -> tactical implementation task
   274	           -> test or UAT evidence
   275	              -> code review confirmation
   276	                 -> as-built documentation update
   277	```
   278	
   279	If a requirement cannot be traced to a test or UAT check, it is not yet implementation-ready.
   280	
   281	### Rule 3: Verification Is a Design Input
   282	
   283	As a consequence of the Verification-First Principle, tests and other verification are planned
   284	before or during architecture and tactical planning, not treated as cleanup after code generation.
   285	
   286	Architecture and implementation plans should identify:
   287	
   288	```text
   289	unit tests
   290	integration tests
   291	security tests
   292	negative tests
   293	migration tests
   294	CLI/UAT scenarios
   295	fixture requirements
   296	acceptance scripts
   297	manual verification steps when automation is not practical
   298	```
   299

   302	### Rule 4: Security and Governance Are First-Class
   303	
   304	Security, governance, identity, permission, audit, and policy behavior must be documented early.
   305	
   306	Any system involving agents, tools, automation, workflow execution, file access, external APIs, user data, secrets, or persistent state must define:
   307	
   308	```text

   310	authorization model
   311	permission boundaries

   313	approval requirements
   314	audit records
   315	failure behavior
   316	revocation or deactivation behavior
   317	data retention and sensitivity rules

   319	```

   323	### Rule 5: Phase Boundaries Must Be Defended
   324

   327	```text

   329	out of scope
   330	deferred features
   331	non-goals
   332	migration boundaries
   333	acceptance criteria
   334	documentation close-out

   338	
   339	If a deferred feature appears necessary, stop and update the plan before implementation continues.

   341	### Rule 6: AI Build Prompts Are Controlled Artifacts
   342	
   343	Prompts used to drive implementation are build artifacts.
   344	
   345	They must be:
   346	
   347	```text
   348	precise
   349	bounded
   350	traceable to authority
   351	explicit about non-goals

   353	explicit about migration behavior
   354	explicit about documentation close-out

   359	Construction directives and large implementation prompts must be preserved with the directive text,
   360	implementing agent identity when known, source authority revisions, and the resulting commit, diff,

   362	treated as unreviewed until a human reviewer reconstructs and accepts the authority record.
   363	
   364	### Rule 7: Code Review Verifies Conformance
   365	
   366	Code review must evaluate whether the implementation matches the documentation authority.
   367	Conformance review must be performed in a context independent of the implementation context.
   368

   371	```text

   378	or broad conversational history unless the exception is explicitly justified in the review report.
   379	The review should record context provenance so future humans and agents can see what the reviewer
   380	was given and what was intentionally excluded.
   381	
   382	Review must check:
   383	
   384	```text
   385	requirement conformance
   386	architecture conformance
   387	security/governance conformance

   390	error handling
   391	migration behavior
   392	deferred-feature boundaries
   393	documentation drift

   459	### Rule 11: The Documentation Scaffold Is Canonical and Architecture-Independent
   460	
   461	The documentation scaffold — the docs/project/ directory tree and the canonical
   462	filenames within it — is fixed and identical for every project, regardless of
   463	technology stack or engineering approach. It is a consequence of Technique
   464	Neutrality: the method owns how work is documented and gated, so the documentation
   465	structure is the method's to fix.
   466	
   467	The code scaffold — source layout, package structure, module organization — is
   468	architecture-determined. The method does not prescribe it. The method only records
   469	it, through the technology-stack decision artifact
   470	(docs/project/decisions/0001-technology-stack.md) and the implementation_paths
   471	field in the project manifest. This is the seam between the canonical documentation
   472	layer and the technique-specific code layer: the method records where code lives so
   473	tooling can reason about it, without dictating where code goes.
   474	
   475	### Rule 12: Supporting Artifacts Attach Through a Typed, Acyclic Reference Graph
   476	
   477	Canonical gate artifacts may reference project-specific supporting artifacts
   478	(produced by whatever analysis or design technique a project uses — a data model,
   479	an object-interaction model, a state-transition model, a user-story set, a UX
   480	specification) through a Supporting Artifacts section. The references form a
   481	directed acyclic graph rooted at canonical gate artifacts:
   482	
   483	```text
   484	the graph is rooted at canonical gate artifacts; a canonical artifact holds the
   485	  Supporting Artifacts section and names the supporting artifacts it references, so
   486	  edges run from the canonical (referencing) artifact to the supporting
   487	  (referenced) artifact
   488	cycles are forbidden and must be flagged
   489	references are one level deep by default; supporting artifacts do not themselves
   490	  carry supporting-artifact references, and greater depth is a declared, justified
   491	  exception
   492	```
   493	
   494	Edge topology and authority direction are distinct. Topology is fixed: the
   495	canonical artifact references the supporting artifact. Authority direction depends
   496	on the relationship type below: for some types the referencing (canonical) artifact
   497	is the one obligated to conform to the referenced artifact, and for others the
   498	reverse. Each type states explicitly which artifact holds authority, so the
   499	coherence obligation is unambiguous regardless of which end holds the reference.
   500	
   501	Each reference carries a relationship type from this bounded vocabulary. In every
   502	case the referencing artifact is the canonical gate artifact, and the referenced
   503	artifact is the supporting artifact it names. The type declares the coherence
   504	obligation and which end holds authority:
   505	
   506	```text
   507	implements     - the referencing artifact realizes a structure the referenced
   508	                 artifact defines. Authority: the referenced artifact. Obligation:
   509	                 every named element in the referencing artifact resolves to a
   510	                 definition in the referenced artifact.
   511	satisfies      - the referencing artifact fulfills requirements the referenced
   512	                 artifact states. Authority: the referenced artifact. Obligation:
   513	                 every requirement in the referenced artifact is covered by the
   514	                 referencing artifact.
   515	tested-by      - the referencing artifact's correctness is verified by the
   516	                 referenced test artifact. Authority: the referencing artifact (the
   517	                 test serves it). Obligation: the referenced test artifact exists,
   518	                 covers the referencing artifact's claims, and passes.
   519	constrained-by - the referencing artifact must not violate limits the referenced
   520	                 artifact sets. Authority: the referenced artifact. Obligation: the
   521	                 referencing artifact contains nothing the referenced artifact
   522	                 forbids.
   523	refines        - the referencing artifact adds detail within the scope the
   524	                 referenced artifact sets. Authority: the referenced artifact.
   525	                 Obligation: the referencing artifact stays within the referenced
   526	                 artifact's scope, adding detail without contradicting or expanding
   527	                 it.
   528	```
   529	
   530	The provenance relationship (which canonical artifact an artifact descends from)
   531	is handled separately by the Derived from provenance header and is not part of this
   532	vocabulary.
   533	
   534	The purpose of this structure is to present coherent context to an AI coding
   535	assistant: the reference graph is the context an agent walks to understand what it
   536	is building, and a cycle or a drifted reference is misleading context.
   537	
   538	### Rule 13: Supporting Artifacts Are Form-Disciplined and Content-Free
   539	
   540	The method constrains the form of a supporting artifact, not its content or name —
   541	a direct consequence of Technique Neutrality.
   542	
   543	```text
   544	form (method-governed):
   545	  filename is a valid lowercase-kebab identifier (no spaces, quotes, or slashes;
   546	    .md extension)
   547	  the artifact lives at the canonical supporting-artifact location in the locked
   548	    scaffold
   549	  it carries the required project front-matter field and its typed relationship to
   550	    what it supports
   551	content and name (technique-governed):
   552	  the artifact is whatever the technique requires, named whatever the technique
   553	    calls it, within the form constraint
   554	```
   555	
   556	Identity is the typed reference edge plus front matter, not the filename; a
   557	supporting artifact may be renamed freely as long as the reference pointing at it is
   558	updated. The authoritative form of a supporting artifact is textual; diagrams are
   559	embedded (for example Mermaid) or referenced from authoritative text, so the
   560	artifact stays diff-able and coherence-checkable.
   561	
   562	### Rule 14: Canonical Artifact Naming
   563	
   564	Per-project artifacts use fixed, role-based filenames that are identical across all
   565	projects. A filename identifies an artifact's role (vision.md, prd.md,
   566	architecture.md, phase-plan.md), never its project. This is a consequence of
   567	Technique Neutrality: the method fixes the form by which an artifact is named and
   568	referenced, so that authority pointers resolve identically for every project.
   569	
   570	```text
   571	the project slug and project name must not appear in any artifact filename or in
   572	  any cross-reference path between artifacts; cross-references use the fixed
   573	  canonical paths
   574	the slug must not be baked into filenames or cross-reference paths; it lives as a
   575	  field in docs/project/project.yaml and is echoed only as the artifact identity
   576	  field below
   577	project identity is carried by location (the docs/project/ tree and the
   578	  repository), by project.yaml, and by a strictly required front-matter field,
   579	  project: <slug>, on every per-project authority artifact (every gate artifact,
   580	  supporting artifact, and the gate log; navigational index files such as
   581	  directory README.md files are exempt)
   582	the project front-matter field must be present and must match the slug in
   583	  project.yaml; it is a checkable provenance claim, not decoration
   584	authority pointers, including AGENTS.md, reference canonical artifacts by their
   585	  fixed full path; because names are project-independent, a single pointer is
   586	  correct for all projects and requires no per-project maintenance
   587	```
   588	
   589	Scaling down a small project may combine or omit content (per the Blast-Radius
   590	Scaling Principle), but it does not float artifact names: a combined or reduced
   591	artifact still uses its canonical role-based name. Naming is fixed independently of
   592	how much content a project's gates carry.

   594	## Documentation Artifact Chain
   595	
   596	The standard documentation chain is:
   597	
   598	```text
   599	1. Vision / Problem Framing
   600	2. Product Requirements Document
   601	3. Architecture Specification
   602	4. Governance and Security Specification
   603	5. Phase Plan (the build partition; certified at G5)
   604	   The following are produced per phase inside the phase loop (G5.x checkpoints):
   605	6. Phase Build Plan
   606	7. Tactical Implementation Plan
   607	8. Construction Directive / Build Prompt
   608	9. Test and UAT Plan (the phase exit test is specified in the phase build plan)
   609	10. Implementation Evidence
   610	11. Code Review Report
   611	12. Remediation Plan / Remediation Prompt
   612	13. Phase Learnings
   613	14. As-Built Documentation Close-Out
   614	15. Traceability Matrix
   615	```
   616	
   617	The phase plan partitions the build into ordered, independently testable phases
   618	and is what G5 certifies. Artifacts 6 through 13 are produced for each phase in
   619	the loop interior to the G5 to G6 span. See docs/methodology/guides/phase-loop.md.
   620	
   621	Not every project needs every document as a separate file. For small projects, multiple artifacts may be combined. The required content must still exist.
   622	
   623	## Artifact Provenance
   624	
   625	Authority and evidence artifacts must identify their origin. A future human or agent should be able
   626	to determine who produced the artifact, when it was produced, whether an agent participated, and
   627	which upstream documents or prompts it was derived from.
   628	
   629	Minimum provenance fields:
   630	
   631	```text
   632	Produced by
   633	Produced on
   634	Produced with
   635	Agent identity
   636	Derived from path and revision
   637	```
   638	
   639	Revision values should be immutable identifiers where practical, such as a commit SHA, tag, pull
   640	request revision, signed release, or other durable artifact identifier. Draft artifacts may use
   641	`TBD` until the upstream source is committed or otherwise pinned.
   642	
   643	If an upstream authority changes after an artifact pins that authority, the downstream artifact is
   644	`Stale` until reviewed and reconciled. Stale artifacts may remain useful context, but they should
   645	not be used as gate evidence without explicit reconciliation.
   646	
   647	## Authority Amendment And Regression
   648	
   649	Accepted authority may be amended when the project learns something material. The methodology does
   650	not require teams to pretend that accepted artifacts are immutable. It requires teams to make the
   651	cost of change visible.
   652	
   653	Amendment cost scales with blast radius:
   654	
   655	```text
   656	editorial change
   657	  -> record if useful; no re-approval
   658	additive-within-scope change
   659	  -> lightweight approval and downstream review
   660	structural change
   661	  -> explicit approval and downstream reconciliation
   662	gate-invalidating change
   663	  -> formal regression to the affected gate
   664	```
   665	
   666	An amendment must identify affected downstream artifacts, traceability rows, plans, tests, reviews,
   667	implementation evidence, deployment evidence, or close-out records. Downstream artifacts that may no
   668	longer match amended authority must be marked `Stale` until reconciled or `Superseded` if replaced.
   669	
   670	Unamended stale authority is a methodology violation. It is not permission for agents to infer new
   671	scope, reinterpret architecture, bypass security/governance rules, or continue a gate transition
   672	using evidence known to be stale.
   673	
   674	## Enforcement Principle
   675	
   676	Methodology rules should be enforced where practical, attested where enforcement is unavailable,
   677	and declared in the active project control plane.
   678	
   679	Projects must state their enforcement class in `docs/project/project.yaml`:
   680	
   681	```text
   682	enforced
   683	attested
   684	```
   685	
   686	`enforced` means a mechanical binding exists, such as hooks, protected-branch checks, policy
   687	automation, or equivalent controls. `attested` means a named human performs or reviews the required
   688	checks on a declared cadence and records attestation in the gate log.
   689	
   690	Attested mode is valid at baseline. It must not become invisible. Exceptions, cadence, required
   691	attester, override policy, and binding paths belong in the project enforcement block. The active
   692	contract is `docs/methodology/guides/enforcement-contract.md`.
   693	
   694	## Measurement Principle
   695	
   696	GenDev projects should emit enough evidence to test whether the methodology is reducing drift,
   697	rework, approval delay, and escaped defects. Measurement must be derived from artifacts this
   698	constitution already requires: gate-log events, approvals, traceability, review results, as-built
   699	records, enforcement overrides, and value reviews.
   700	
   701	Measurement must not become a separate bureaucracy. At baseline, metrics are computed on demand
   702	from project records, and phase close-out may snapshot the generated report. Outcome metrics outrank
   703	activity metrics. A high finding count is not automatically good, a low finding count is not
   704	automatically good, and success criteria cannot be redefined after delivery to make the project look
   705	successful.
   706	
   707	Every G1 vision must define success criteria with a measure, target, read timing, owner, and
   708	evidence source. Production or value-bearing releases must eventually report those criteria as
   709	`met`, `missed`, or `unmeasurable`.

  1124	## Process Gates
  1125	
  1126	The canonical gate enumeration and detailed entry/exit criteria live in
  1127	docs/methodology/guides/gates.md. The enumeration below must remain synchronized
  1128	with that document. In any conflict, gates.md controls.
  1129	
  1130	### G0: Project Initialized
  1131	
  1132	Exit criteria:
  1133	
  1134	```text
  1135	manifest paths are syntactically valid
  1136	starter docs exist
  1137	current gate is recorded as G1
  1138	```
  1139	
  1140	### G1: Vision Ready
  1141	
  1142	Exit criteria:
  1143	
  1144	```text
  1145	problem statement is clear
  1146	target users are clear
  1147	success criteria are measurable and include read timing
  1148	non-goals are explicit
  1149	blocking open questions are assigned
  1150	```
  1151	
  1152	### G2: Requirements Ready
  1153	
  1154	Exit criteria:
  1155	
  1156	```text
  1157	every baseline requirement has acceptance criteria
  1158	requirements are specific enough for architecture and tests
  1159	deferred items have reasons
  1160	open questions that block architecture are resolved or assigned
  1161	```
  1162	
  1163	### G3: Architecture Ready
  1164	
  1165	Exit criteria:
  1166	
  1167	```text
  1168	architecture rules trace to requirements
  1169	ownership boundaries are clear
  1170	state and lifecycle are defined
  1171	stack decision is accepted
  1172	implementation does not need to invent core structure
  1173	```
  1174	
  1175	### G4: Governance Ready
  1176	
  1177	Exit criteria:
  1178	
  1179	```text
  1180	every actor has permitted and forbidden actions
  1181	authorization rules include positive and negative tests
  1182	audit requirements are explicit
  1183	secrets and sensitive data handling are defined
  1184	agent/tool stop conditions are documented or marked N/A
  1185	```
  1186	
  1187	### G5: Build Ready
  1188	
  1189	Exit criteria:
  1190	
  1191	```text
  1192	the build is partitioned into ordered, independently testable phases
  1193	every phase carries a stable id label; order is defined by the phase plan
  1194	the requirement coverage map accounts for all in-scope requirements
  1195	integration criteria are declared
  1196	the partitioning rationale records the sizing criterion
  1197	```
  1198	
  1199	The G5 to G6 span has an interior phase loop: while current gate stays G5, the
  1200	build proceeds one phase at a time through interior checkpoints (`G5.x`) that
  1201	produce each phase's planning artifacts and record its exit. Checkpoints are not
  1202	gates; `G5.0` is the phase plan checkpoint, not a gate transition. Current
  1203	gate remains G5 through all `G5.x`.
  1204	
  1205	The canonical definition is in docs/methodology/guides/gates.md ("G5 Interior:
  1206	The Phase Loop") and docs/methodology/guides/phase-loop.md.
  1207	
  1208	### G6: Implementation Ready For Review
  1209	
  1210	Exit criteria:
  1211	
  1212	```text
  1213	all declared phases have closed phase-exit checkpoints
  1214	aggregate regression suite is green at the candidate revision
  1215	integration criteria are satisfied or carried forward as explicit residuals
  1216	implementation summary and evidence are complete enough for one conformance cycle
  1217	```
  1218	
  1219	### G7: Acceptance Ready
  1220	
  1221	Exit criteria:
  1222	
  1223	```text
  1224	critical findings are remediated
  1225	major findings are remediated or explicitly accepted with rationale
  1226	tests and UAT evidence exist
  1227	residual risk is documented
  1228	traceability matrix reflects actual status
  1229	```
  1230	
  1231	### G8: Deployment Ready
  1232	
  1233	Exit criteria:
  1234	
  1235	```text
  1236	deployment/release scope is accepted
  1237	deployment approvals, command/rollback plan, runbook, and monitoring are defined
  1238	production-impacting migrations and security implications are approved
  1239	post-deployment owner, value-review disposition, and validation trigger are defined
  1240	if not deploying, a non-deployment disposition is explicitly accepted
  1241	```
  1242	
  1243	### G9: As-Built Closed
  1244	
  1245	Exit criteria:
  1246	
  1247	```text
  1248	future agents can understand the actual system without chat history
  1249	implemented behavior, deferred behavior, and deviations are explicit
  1250	deployment/validation outcomes and operational disposition are recorded
  1251	test evidence is complete and traceable
  1252	project status is closed for this iteration or release
  1253	```

  1477	## Appendix A: Reusable AI Prompt Library
  1478	
  1479	This appendix provides reusable prompts for applying this constitution with AI-assisted engineering tools.
  1480	
  1481	The prompts are intentionally verbose. Their purpose is to reduce ambiguity, control scope, preserve traceability, and prevent AI-assisted phase drift.
  1482	
  1483	Use these prompts as templates. Replace bracketed values with project-specific context.
  1484	
  1485	### Prompt 1: Vision and Problem Framing
  1486	
  1487	Use when starting a new product, major feature, or refactor before writing requirements.
  1488	
  1489	```text

  1493	
  1494	The document must include:
  1495	
  1496	- problem statement;
  1497	- target users or operators;
  1498	- user pain or opportunity;
  1499	- desired outcomes;
  1500	- success criteria;
  1501	- non-goals;
  1502	- major assumptions;
  1503	- major risks;
  1504	- initial security, governance, or compliance concerns;
  1505	- likely testability implications;
  1506	- open questions that must be answered before writing a PRD.
  1507	
  1508	Do not write implementation details yet.
  1509	
  1510	Ask any clarifying questions that would materially improve the document before drafting. If assumptions are necessary, state them explicitly.
  1511	```

     1	# Repository Engineering Policy
     2	
     3	Status: Reusable operating policy
     4	Authority: AGENTS.md and docs/methodology/constitution/gendev.md
     5	Derived from: the active project integration; provenance is recorded in the v3 migration inventory.
     6	
     7	## Purpose and authority
     8	
     9	This policy governs engineering work in the active project. It supplements
    10	[AGENTS.md](../../AGENTS.md) and the
    11	[GenDev constitution](../methodology/constitution/gendev.md). Use the authority
    12	precedence defined in AGENTS.md; this document introduces no competing order.
    13	Accepted project governance, architecture, requirements, and approved phase
    14	authority remain controlling for their scope. Stop and surface a conflict
    15	rather than silently choosing a lower-level rule.
    16	
    17	The [task lifecycle policy](development-task-lifecycle.md) governs execution and
    18	handoff. The [independent validation policy](independent-validation-policy.md)
    19	governs conformance review. Confirmed pre-existing findings belong in the
    20	[policy debt register](legacy-policy-debt.md).
    21	
    22	These are repository operating rules. Their adaptation does not accept the
    23	project's draft specifications, grant product implementation authority, or
    24	advance a GenDev gate.
    25	
    26	## Scope and current layout
    27	
    28	Apply this policy to product source, product tests, dependency declarations,
    29	lockfiles, runtime configuration, and documents that define product contracts.
    30	
    31	Product source layout, language/toolchain, tests, runtime configuration, and
    32	implementation paths are defined by the active project's accepted architecture,
    33	stack decision, phase plan, and manifest. No sample application's paths or
    34	Python version are inherited by this policy.
    35	
    36	In an installed project, the installation record identifies baseline-owned
    37	files. Local policies, board/task state and additional skills are project-owned.
    38	Use the distribution's conflict-aware upgrade path; never update integrity
    39	hashes merely to hide an unapproved change. In the methodology source repository,
    40	baseline engineering follows its explicitly authorized migration/evolution plan
    41	and remains separate from any initialized product's gates.
    42	
    43	## Before implementation
    44	
    45	Run the GenDev doctor and project-state command. Read the manifest, active
    46	artifact, approval record, and governing directive. Report the current gate,
    47	approval state, and next authorized work.
    48	
    49	Product implementation requires the accepted upstream authority and phase
    50	checkpoints specified by GenDev. The initialized draft scaffold is not build
    51	authority. At G1, framing and authorized environment or policy maintenance may
    52	proceed; product code generation awaits the required authority.
    53	
    54	Preserve unrelated changes. Inspect branch and checkout ownership before
    55	editing, committing, or integrating. Stage only files belonging to the
    56	current task when a commit is authorized.
    57	
    58	## Design and interface rules
    59	
    60	Apply GenDev's six principles: YAGNI, KISS, DRY, SRP, least astonishment, and no
    61	undeclared authority-bearing abstractions. Use existing logic and keep each
    62	unit responsible for one coherent task.
    63	
    64	When components or public interfaces exist, use documented contracts rather
    65	than internal reach-through or incidental side effects. A contract change
    66	must identify affected consumers, migration needs, tests, and documentation.
    67	Do not introduce packages, interfaces, schemas, or dependencies merely to
    68	satisfy a hypothetical future need.
    69	
    70	Structured data crossing a persistent, external, or component boundary must
    71	have an explicit contract. Use the simplest suitable representation. A typed
    72	dataclass, typed dictionary, or validation library may be appropriate; this
    73	policy does not select or install a new library.
    74	
    75	## Typing and runtime invariants
    76	
    77	For new or materially changed Python product code:
    78	
    79	- annotate public functions and boundary methods, including return types;
    80	- make exchanged values and failure behavior explicit;
    81	- justify `Any` at dynamic boundaries rather than propagating it;
    82	- prefer validation and stronger contracts over repeated casts; and
    83	- avoid blanket source suppressions or weakening type-checker configuration.
    84	
    85	Tests may use narrow, justified relaxations for dynamic fixtures and doubles.
    86	Test ergonomics do not justify hiding source defects. Pre-existing exceptions
    87	must be recorded as debt rather than silently treated as compliant.
    88	
    89	Use explicit exceptions or validation for external inputs, configuration,
    90	authorization, persistence, and essential lifecycle requirements. Use `assert`
    91	only for internal programmer checks whose removal cannot weaken required
    92	runtime behavior. A cast needs an already-established invariant and must
    93	narrow to the actual contract; it cannot substitute for validation.
    94	
    95	## Verification and available tooling
    96	
    97	Define verification before product implementation in the phase build plan,
    98	tactical plan, construction directive, and test/UAT plan. Cover the meaningful
    99	positive, negative, regression, boundary, and failure cases for that scope.
   100	Do not add tests that merely repeat implementation wording.
   101	
   102	The available repository checks are:
   103	
   104	```sh
   105	./scripts/gendev-doctor.sh
   106	./scripts/project-state.sh
   107	./scripts/check-methodology.sh
   108	./scripts/test-methodology.sh --suite shell-syntax
   109	```
   110	
   111	The first three orient and validate the installed project. The shell suite is
   112	appropriate when shell tooling or its integration changes. These checks do
   113	not establish product correctness, independent verification, or acceptance.
   114	
   115	No product linter, product test runner, or type checker is currently declared
   116	in `pyproject.toml`. Select and configure any such tools through the accepted
   117	stack and implementation plan. Do not report Ruff, pytest, or mypy as existing
   118	repository gates or install them just to satisfy this imported policy.
   119	
   120	PyYAML is declared separately in the `devboard` tooling dependency group.
   121	For board changes and task selection, run board validation. For board code or
   122	schema changes, also run the focused standard-library test suite:
   123	
   124	```sh
   125	uv run --no-project --with-requirements requirements-devboard.txt python scripts/devboard.py validate
   126	uv run --no-project --with-requirements requirements-devboard.txt python -m unittest discover -s tests/devboard -v
   127	```
   128	
   129	These checks cover task-tracking behavior, not product tests, independent
   130	conformance, authenticated approval, or remotely reconciled delivery.
   131	
   132	Source and installed-product workflows run their context-appropriate checks
   133	when hosted and enabled. Its presence is not evidence that a hosted run, branch protection,
   134	or local hook is active. Enforcement remains as declared in the project
   135	manifest; full filesystem access does not grant project approval.
   136	
   137	## Review, exceptions, and closeout
   138	
   139	Applicable implementation must receive independent conformance review under
   140	the validation policy before it is proposed as complete. Passing commands or
   141	a builder's report do not substitute for that review or human acceptance.
   142	
   143	A policy exception identifies the named human, date, scope, requirement,
   144	reason, risk, validation, and expiry or follow-up. It cannot silently override
   145	the constitution, accepted security requirements, or a required gate. Use the
   146	GenDev amendment or override protocol when those controls are affected.
   147	
   148	Update test/UAT evidence, review findings, remediation disposition, as-built
   149	records, and traceability as applicable. Report omitted checks and known
   150	limits. Keep verification, human acceptance, delivery, and deployment distinct.

================ docs/policies/independent-validation-policy.md ================
     1	# Independent Validation Policy
     2	
     3	Status: Reusable operating policy
     4	Authority: AGENTS.md and docs/methodology/constitution/gendev.md
     5	Derived from: the active project integration; provenance is recorded in the v3 migration inventory.
     6	
     7	## Purpose and authority
     8	
     9	This policy defines independent conformance review for the active project. It
    10	supplements [AGENTS.md](../../AGENTS.md), the
    11	[engineering policy](repository-engineering-policy.md), and the
    12	[task lifecycle policy](development-task-lifecycle.md). GenDev authority and
    13	the accepted project specifications control; this policy cannot waive them.
    14	
    15	Independent review answers whether a stable candidate conforms to its named
    16	authority. It does not accept the project, approve a gate, authorize delivery,
    17	or establish deployment readiness.
    18	
    19	## Applicability and documentation maintenance
    20	
    21	Product code, behavioral tests, dependency/environment changes, runtime
    22	configuration, migrations, and public contract changes require independent
    23	review proportionate to their scope before being proposed as complete.
    24	GenDev's independent-context rule applies even when deterministic checks pass.
    25	
    26	A bounded documentation-only maintenance request may use a direct user
    27	authorization record, scope description, accuracy pass, link checks, and
    28	methodology checks. It does not automatically require a new construction
    29	directive or a formal frozen-candidate report. Record who requested the work,
    30	the scope, checks, and limitations in the relevant artifact or task evidence.
    31	
    32	This maintenance route does not approve product specifications, waive a
    33	mandatory review in accepted authority, or cover runtime, dependency,
    34	enforcement-code, or security-behavior changes. If the task crosses those
    35	boundaries, stop and obtain the required authority. Rewriting policy documents
    36	must not be reported as formal independent VERIFIED evidence.
    37	
    38	## Roles and independence
    39	
    40	The human approver owns scope, risk, required artifact acceptance, and gate
    41	approval. The controller owns bounded dispatch and evidence reconciliation.
    42	The builder implements authorized work. A validator reviews the frozen
    43	candidate read-only. A remediator changes only the authorized findings.
    44	
    45	The builder may also be the controller, but may not validate its own candidate
    46	or remediation. An independent human reviewer or a separate fresh-context
    47	agent may perform the validation. A different model is optional; independent
    48	context is mandatory. A skill or enabled capability is not authorization to
    49	start additional agents.
    50	
    51	A reviewer receives pinned authority, the selected candidate diff and relevant
    52	surrounding code, requirements, and permitted verification evidence. Do not
    53	supply the builder's session transcript, private reasoning, or conclusions as
    54	proof. A justified context exception must be recorded with its limits.
    55	
    56	## Candidate and required request
    57	
    58	Formal validation needs a stable candidate commit and an exact base/candidate
    59	diff. Uncommitted work can receive advisory review but not formal VERIFIED.
    60	The repository must have an initial commit before this process is available.
    61	
    62	Before dispatch, prepare a request containing:
    63	
    64	- project and phase identity, work-unit or tactical task IDs, and review mode;
    65	- base commit, candidate commit, branch or checkout identity, and exact diff;
    66	- controlling authority paths with revisions or hashes and artifact status;
    67	- the approved construction directive and acceptance criteria;
    68	- relevant architecture rules, including the accepted domain model;
    69	- required commands and expected behavioral, design, and implementation evidence;
    70	- known baseline failures, exclusions, and explicitly approved exceptions;
    71	- permitted external effects, credential use, and costs, if any; and
    72	- exact repository locations for the request, report, and evidence.
    73	
    74	For board-tracked work, include its task ID and link the same canonical phase
    75	authority and evidence from its tracking index. Use tactical identifiers from
    76	the actual approved plan; a board label does not approve that plan. Missing,
    77	stale, contradictory, or unapproved authority blocks formal validation.
    78	
    79	## Evidence locations and provenance
    80	
    81	Use the canonical phase code-review report referenced by the manifest for
    82	phase review. Store detailed phase requests and evidence beside their phase
    83	artifacts, and aggregate review support under `docs/project/review/`.
    84	Reference these records from the canonical review report, traceability, and
    85	as-built closeout as appropriate. Choose exact paths in the request rather
    86	than inventing a separate planning packet or board schema.
    87	
    88	Record project identity, reviewer identity/model where known, review-context
    89	creation time, review mode, candidate/diff identity, authority revisions,
    90	shared-context exceptions, commands, results, skipped checks, and residual
    91	risk. Include the GenDev provenance fields on authority and evidence artifacts.
    92	
    93	## Read-only review procedure
    94	
    95	1. Read AGENTS.md, these local policies, and every authority named in the request.
    96	2. Confirm candidate stability, checkout ownership, authority pins, and diff bounds.
    97	3. Map every acceptance criterion and directive task to implementation and evidence.
    98	4. Inspect the complete selected diff and relevant surrounding code for drift,
    99	   undeclared abstractions, duplication, contract violations, and deferred scope.
   100	5. Evaluate GenDev's six code-quality principles and the required behavioral,
   101	   design, security, failure-path, migration, and implementation checks.
   102	6. Run authorized commands and separate pre-existing failures from regressions.
   103	7. Reconcile documentation, configuration, traceability, and closeout obligations.
   104	8. Return exactly one outcome with reproducible evidence and stated limits.
   105	
   106	Do not edit or remediate the candidate, change project state, commit, push,
   107	merge, release, deploy, or send external messages. Read-only review may create
   108	ordinary disposable test outputs only when the request permits them; it must
   109	not mutate governed files or persistent application state. Never print or
   110	persist credentials. If a required command needs an unauthorized effect or
   111	cannot respect those boundaries, omit it and report the resulting blocker.
   112	
   113	## Review modes and outcomes
   114	
   115	A full review covers the complete selected work-unit scope. A delta review
   116	checks specified remediation and regressions against the new candidate. An
   117	aggregate review covers the complete integration or phase scope before its
   118	required closeout; delta review alone does not establish integration conformance.
   119	
   120	Return VERIFIED only when all mandatory criteria and checks have cited
   121	evidence, any permitted exception is explicitly recorded, no mandatory
   122	requirement is violated, no blocker/critical/high finding remains, and the
   123	required closeout evidence is reconciled. Advisory suggestions may remain;
   124	an uncited assertion cannot support VERIFIED.
   125	
   126	Return CHANGES_REQUESTED when the candidate violates authority or needs
   127	remediation. Every finding identifies its stable ID, severity, location,
   128	violated requirement, evidence, risk, fix, required verification, and
   129	configuration/documentation impact.
   130	
   131	Return BLOCKED when authority, candidate stability, acceptance criteria,
   132	infrastructure, or permitted evidence is insufficient. Identify checks already
   133	performed, the exact blocker, and what would resolve it. BLOCKED is not a code
   134	failure or a formal verification result.
   135	
   136	A human may separately accept a documented risk within their authority. That
   137	decision does not rewrite a validator's result or turn unmet mandatory review
   138	conditions into VERIFIED. Resolve governing exceptions through GenDev's
   139	approval/amendment process and review the resulting candidate as required.
   140	
   141	## Remediation and stale candidates
   142	
   143	The controller converts each numbered finding into a bounded remediation
   144	directive with tests, documentation, acceptance criteria, and non-goals. The
   145	original builder may perform authorized mechanical fixes. Use independent
   146	expertise when the risk or accepted plan requires it; do not start extra agents
   147	without the applicable delegation authority.
   148	
   149	Commit the corrected candidate when authorized, retain the old report as
   150	historical/superseded evidence, and obtain a fresh review of the new revision.
   151	After two unsuccessful remediation cycles, return unresolved findings and
   152	options to the human instead of continuing automatically.
   153	
   154	A change to reviewed code, tests, runtime configuration, governing authority,
   155	or the candidate revision makes a running review stale. Stabilize and request
   156	a new independent review; do not reuse the old conclusion. Evidence-only
   157	closeout additions may be reviewed as such, but do not excuse changes to the
   158	governed candidate.
   159	
   160	## Acceptance boundary
   161	
   162	VERIFIED permits a recommendation for human acceptance or the next authorized
   163	checkpoint. It is not acceptance, phase exit, deployment approval, or a gate
   164	transition. Record those decisions through the GenDev gate-log and manifest
   165	process only when the named human has actually made them.
